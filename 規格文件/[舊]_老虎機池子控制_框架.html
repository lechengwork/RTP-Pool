用一個「池子」
保證 RTP 收斂

Outcome Controller 設計框架 — 一次開發,套用到 100+ 款遊戲;遊戲本身的機率數學完全不動。

從問題開始

客戶想要的兩件事

需求 01

Recovery(連敗補償)

玩家連續很多次都沒中獎時,希望有機會讓他早一點中一次,減少挫折感。

需求 02

新手保護

新手玩家剛開始玩的時候,不希望他一開局就中到超大獎。

這兩個需求都是要「調整玩家看到的結果」,但又不能破壞遊戲原本的回饋比例。

為什麼不能直接改遊戲

限制:數學不能動

  • 公司有 100+ 款遊戲,每一款的機率設計都不一樣。 每款的 RTP 都已經設計好、驗證過,不能隨便更動。
  • 如果每個需求都要求每款遊戲各自去改機率邏輯 → 開發成本爆炸。
  • 結論:需求必須統一在遊戲「之外」處理,遊戲數學保持原樣。

解法第一步

在中間加一層 Controller

但這一層自己製造了一個風險

「如果這層可以為了客戶需求去挑結果,
怎麼保證我們不會破壞掉那個
已驗證、不能動的 RTP?」

我們需要一個「守門員」,隨時知道現在離目標 RTP 差多少,而且能把它拉回來。

這個守門員,就是接下來的池子。

核心

池子:一個(機台 × RTP版本)一個,跨所有 BetType

B累積總押注  Σ TotalBet
D紀錄數值(欠款) Σ (TotalBet · r − TotalWin),  r = 目標RTP
ε允許誤差
D / B = (B·r − W) / B = r − W/B = 目標RTP − 實際RTP

池子以 version(RTP) 為 key;同版本下所有 BetType(Normal / BuyFeature / ExtraBet…)都是同一目標 RTP,故共用單一 r,記帳零帶偏。

精確等式,不是近似。   D>0 → RTP 偏低(欠玩家);  D<0 → RTP 偏高(多給了)。每次最終結果結算後更新池子。

一句話理解整套設計

客戶需求負責借,收斂負責還

政策層(客戶需求,可變)與收斂保證層(池子,不變)解耦 — 客戶需求怎麼改,RTP 收斂保證都不變。
個人干涉由群體共用池吸收:玩家 A 的 Recovery 擾動共用池,間接影響玩家 B 之後是否被收斂干涉。

狀態存在哪

兩種範圍的狀態

全域 · per version

池子 B / D / ε(或 λ)

把該版本上所有玩家加總的單一共用數字,只負責一件事:群體 RTP 收斂。

個別 · per player

連敗數 · 新手局數

客戶需求邏輯用來判斷「這個玩家」何時觸發 Recovery / 新手保護,每位玩家各存一份。

兩者是不同範圍、不衝突:個別玩家的干涉會擾動共用池,再由收斂邏輯從群體層面還回去 —— 就是「借 / 還」。

Controller 裡有兩塊邏輯 · 每次只走一塊

定案的派工規則

# 暖身期:B 或樣本數未達門檻 → 收斂完全不介入
if 尚在暖身期:
    if 有客戶需求觸發:  走「客戶需求邏輯」   # 新手保護就在這階段
    else:               正常 Spin(要 1 次)
else:
    if |D/B| ≥ ε_hard:  走「收斂邏輯」        # ① 壓力過大→收斂反超
    elif 有客戶需求觸發: 走「客戶需求邏輯」
    elif |D/B| > ε:      走「收斂邏輯」
    else:               正常 Spin(要 1 次)

結算 → 更新池子(不論走哪塊都更新 B、D)
① 壓力過大時收斂反超客戶需求(ε_hard);暖身期收斂全關、但客戶需求照跑。兩塊永遠互斥,每局只走一塊。

收斂邏輯怎麼運作

以 ε 為界,決定要不要干涉

|D/B| ≤ ε

正常跟數學要 1 次結果,直接輸出。

|D/B| > ε

跟數學要 N 次,挑讓 |D/B| 最小的那個輸出 — 方向自動雙向修正。

暫定 ε = 2%、ε_hard = 2ε(壓力門檻)、暖身門檻另定 —— 均待與顧問敲定。

⑥ 待跟顧問二選一

池子怎麼累加?兩案並陳

案 A · 終身 + 重整

終身累加,超上限時等比重整

B、D 終身累加;B 超上限時 B、D 同除以 k(比值 D/B 不變),搭配整數記帳避免浮點漂移。

保證「終身」RTP 收斂,對外故事最強。
風險:B 越大越遲鈍,D/B ~ 1/√N,晚期才冒出的偏差抓不動。

案 B · 衰減池 EWMA

只反映近期,天生有界

B ← λ·B + TotalBet
D ← λ·D + (TotalBet·r − TotalWin)

記憶長度 ≈ 1/(1−λ);永遠對近期敏感、永遠有界(順帶解掉溢位)。
保證「近期」RTP 收斂,運維導向。代價:保證從「終身」變「近期」;λ 是新旋鈕。

恆等式精神兩案都保留(D/B 仍是 目標−實際 RTP);差別只在終身 vs 近期與反應速度。

守住的三條底線

這套設計不會越線

底線 01

不捏造結果

給玩家的一定是遊戲真實抽出來的其中一個,系統只是幫忙「挑」。

底線 02

不收回到手的錢

頂多是「這次不多給」,絕不會把已經中獎的錢拿回去。

底線 03

數學完全不動

遊戲本身的機率設計不改,一次開發,套用到所有遊戲。

設計已定案 · 剩幾個旋鈕

要跟顧問敲定的事

ε

允許誤差 —— 暫定 2%。全機台同一個,還是 per 版本可調?

ε_hard

壓力門檻(收斂反超客戶需求)—— 建議 2ε。

暖身門檻

累積 B 或樣本數達標才啟用收斂 —— 初值待定。

λ / 累加

終身+重整 vs 衰減池(EWMA)—— 見前頁,兩案並陳。

N

干涉時的重轉次數 —— 沿用現有(例:5)。

已定案的設計前提:同版本所有 BetType 同一目標 RTP(單一 r 記帳);個人干涉由群體共用池吸收。剩下的只是上面這些數值。
