# RTP 水池控制機制 — Server 實作規格

> 對象：後端／Server 工程師。本文件說明要建置的資料模型、參數、每轉處理流程與邊界情況。數學背景與設計理由請參閱《概念說明》文件；本文件聚焦「怎麼做」。

> 修訂註記（2026-09-15）：核心邏輯未變。本版補入合規定位（§0）、參數三元組耦合關係的強化（§10）、telemetry / 事件 log 需求（§11）、並行一致性的實作抉擇（§9.2）、「機率觸發」評估後暫緩的紀錄（§7.1），以及**階段實作計畫（§13）**。**命名同步：本規格所建置的池正式命名為「RTP基本池」（RTP Basic Pool）。**

---

## 0. 適用市場與合規定位

本機制以「候選挑選」修正 RTP（見 §6），屬**下注後的 outcome steering**：聚合層面公平（賠付表／機率未動），但單轉期望值在修正期間不等於 r。**定位於灰色／社交幣／Class II 型市場**；GLI／BMM 等要求「結果於下注當下決定、事後不得挑選」的受監管市場恐無法通過認證。上線前依目標市場確認法遵範圍。

---

## 1. 目的與範圍

為每一個（總代 × 老虎機 × RTP 版本）組合維護一個「水池」，即時追蹤其近期實際 RTP 與目標值的偏差，並在偏差超過動態帶寬時，透過「候選結果挑選」把偏差拉回。

> 命名：本規格所建置的這個池正式命名為「**RTP基本池**」（RTP Basic Pool）。下文的「水池／池」皆指 RTP基本池；資料表、log、程式命名建議統一以此為準（例如 `rtp_basic_pool`）。

前提假設：

1. **本公司老虎機每一轉都能一次結算完成**（沒有跨轉、無法立即結束的 feature），因此每個候選結果的派彩值在當轉即為確定值。
2. **同一個 RTP 版本下的所有玩法（基本押注、1.5× 強化、高倍購買遊戲等），在數學設計上其原生 RTP 皆保證 = r。** 因此所有玩法共用同一個水池（key 不含玩法），且不需監控各玩法的下注佔比。總代以「遊戲層級（含所有玩法）」的 RTP 為對帳口徑，故水池亦以此為控制目標。
3. **購買類型玩法（高額直購）一律只記帳、不參與候選挑選**（見第 8 節）。此決策已用兩款遊戲真實細單驗證：購買為全場波動最低、對水池擾動最小的玩法，留在池中記帳成本極低。

## 2. 名詞與符號

| 符號 | 說明 |
|---|---|
| `r` | 目標 RTP，由 RTP 版本決定（例如 0.94） |
| `bet` | 該轉的總下注（TotalBet） |
| `win` | 該轉的實際派彩（一次結算完成的總派彩） |
| `isBuyType` | 該轉是否為「購買類型」玩法（由遊戲／下注類型傳入）。`true` = 只記帳、**不參與候選挑選** |
| `Dl` | 水池狀態：EWMA 加權的 Σ(r·bet − win)（水位） |
| `Bl` | 水池狀態：EWMA 加權的 Σ bet |
| `W`  | 水池狀態：EWMA 加權的轉數計數 |
| `metric` | 目前偏差 = `Dl / Bl` = 目標RTP − 近期實際RTP |
| `band` | 當前動態容許帶寬 |

## 3. 資料模型

### 3.1 水池 Key

複合主鍵：**（總代 ID, 老虎機 ID, RTP 版本 ID）**。每個組合一筆水池記錄。

### 3.2 每個水池的狀態欄位（persist 於 DB）

| 欄位 | 型別 | 初始值 | 說明 |
|---|---|---|---|
| `Dl` | double | 0.0 | 加權水位 Σ(r·bet − win) |
| `Bl` | double | 0.0 | 加權下注 Σ bet |
| `W`  | double | 0.0 | 加權轉數計數 |
| `overrideMode` | enum | `AUTO` | 手動覆寫：`AUTO` / `FORCE_ON` / `FORCE_OFF` |

> 只需三個 double 加一個 enum。`Dl`、`Bl`、`W` **三者都用同一個 λ 每轉衰減**，語意一致。

### 3.3 全域常數（全平台共用一組）

| 常數 | 值 | 說明 |
|---|---|---|
| `LAMBDA` | 0.9999975 | EWMA 遺忘係數。記憶窗 1/(1−λ) ≈ 400,000 轉 |
| `EPSILON` | 0.05 | 容許誤差（動態帶寬的下限 / 穩態帶寬） |
| `K` | 3 | 帶寬的 σ 倍數（3σ → 不易誤觸發） |
| `VOL` | 15 | 全平台假設的最高波動係數（就高不就低） |
| `W_MIN` | 10000 | 啟動門檻；`W < W_MIN` 完全不控制 |
| `N` | 10 | 候選數（控制強度，**待調**，見第 10 節） |

> 這五個常數不是各自獨立的：`LAMBDA`、`EPSILON`、`VOL` 是一組**校準三元組**，改一個要連動重算其餘（見 §10）。

## 4. 每轉處理流程

每一次 spin 請求，依序執行：

1. **判斷控制是否啟用**（依 `overrideMode` 與 `W`；**購買類型玩法 `isBuyType == true` 一律不啟用**）。
2. **計算目前偏差 `metric` 與動態帶寬 `band`**。
3. **產生結果**：若控制啟用且 `|metric| > band` → 走候選挑選；否則單一公平抽樣。
4. **更新水池三個累積值**（先乘 λ 衰減、再加當轉）。**所有轉都要更新，購買類型也不例外。**
5. **原子性寫回** DB。
6. **（新增）寫一筆事件 log**（見 §11），供上線後調參與稽核。

### 4.1 Pseudocode

```text
CONSTANTS:
  LAMBDA  = 0.9999975
  EPSILON = 0.05
  K       = 3
  VOL     = 15
  W_MIN   = 10000
  N       = 10

function onSpin(pool, bet, r, isBuyType):

  # --- 1. 控制是否啟用 ---
  if    isBuyType                     : controlOn = false   # 購買類型：只記帳、不挑選
  elif  pool.overrideMode == FORCE_OFF: controlOn = false
  elif  pool.overrideMode == FORCE_ON : controlOn = true
  else: # AUTO
        controlOn = (pool.W >= W_MIN)

  # --- 2. 目前偏差與動態帶寬 ---
  metric = (pool.Bl > 0) ? (pool.Dl / pool.Bl) : 0.0
  effW   = max(pool.W, 1.0)                          # 防除以 0
  band   = max(EPSILON, K * VOL / sqrt(2.0 * effW))  # 資料少→帶寬寬；資料多→收到 EPSILON

  # --- 3. 產生結果（確定性觸發；機率觸發評估後暫緩，見 §7.1） ---
  triggered = controlOn AND abs(metric) > band
  if triggered:
      candidates = engine.generateCandidates(N)      # N 個「照原生機率」抽出的合法結果
      target     = r * bet + LAMBDA * pool.Dl        # 讓更新後 Dl≈0 的理想 win
      result     = argmin over c in candidates of abs(c.win - target)
  else:
      result     = engine.generateOne()              # 單一公平抽樣

  # --- 4. 更新水池（先衰減，再加當轉）；所有轉都更新，含購買類型 ---
  pool.Dl = LAMBDA * pool.Dl + (r * bet - result.win)
  pool.Bl = LAMBDA * pool.Bl + bet
  pool.W  = LAMBDA * pool.W  + 1.0

  # --- 5. 原子性寫回 ---
  persist(pool)

  # --- 6. 事件 log（見 §11）---
  logSpin(pool.key, bet, result.win, r, isBuyType, metric, band, triggered, N)

  return result
```

## 5. 關鍵公式彙整

| 項目 | 公式 | 備註 |
|---|---|---|
| 偏差指標 | `metric = Dl / Bl` | = 目標RTP − 近期實際RTP |
| 動態帶寬 | `band = max(EPSILON, K·VOL / sqrt(2·W))` | `2·W` ≈ EWMA 有效樣本數 |
| 理想派彩 | `target = r·bet + LAMBDA·Dl` | 令更新後 `Dl ≈ 0` |
| 候選挑選 | `argmin |c.win − target|` | 在 N 個候選中選 |
| 更新 Dl | `Dl ← LAMBDA·Dl + (r·bet − win)` | 先衰減後加 |
| 更新 Bl | `Bl ← LAMBDA·Bl + bet` | 同上 |
| 更新 W  | `W ← LAMBDA·W + 1` | 同上 |

**帶寬隨資料量變化的對照（VOL=15, K=3）：**

| W（≈加權累積轉數） | band |
|---|---|
| 10,000（啟動門檻） | ≈ 31.8% |
| 90,000 | ≈ 10.6% |
| 200,000 | ≈ 7.1% |
| 400,000（窗填滿） | ≈ 5.0%（觸底＝EPSILON） |

> 實測參考：兩款高流量遊戲（0940 版）跑一整週真實資料，暖機後帶寬全程落在 6.4%～31.8%，`|metric|` 離觸發線最近仍差約 4%，觸發率 0%。屬預期行為（平常不介入），非 bug。

## 6. 候選挑選細節

1. **候選必須是原生分布抽樣**：`engine.generateCandidates(N)` 產出的每個候選，都要是「照這台遊戲原本機率、獨立抽樣」的合法結果。不得偏改賠付表或中獎機率——本機制只在真實可能發生的結果中「選擇」，不捏造。
2. **派彩值為當轉確定值**：因遊戲一次結算完成，`c.win` 直接可得，不需模擬延遲 feature。
3. **選擇規則**：計算 `target = r·bet + LAMBDA·Dl`，選 `|c.win − target|` 最小的候選。
4. **漸進修正是內建的**：若需要大獎但候選中無夠大者，`argmin` 會自然選到現有最大者，一次補一點——不需額外邏輯。（此即《概念說明》§6.3 所述「上修較弱」的來源，為刻意接受的取捨。）
5. **收手是內建的**：因為每轉獨立判斷 `|metric| > band`，一旦偏差回到帶內，下一轉就走單一公平抽樣，自動恢復自由跑（無需額外 hysteresis 狀態）。
6. **不設單注 cap**：已評估「夾住每轉對 `Dl` 的貢獻」以防單一巨獎衝擊，**決定不採用**——高波動遊戲合法賠付上看 1500×，能壓住巨獎的 cap 會同時砍掉合法派彩、使控制器偏移並狂觸發（實測 cap=50×bet 時觸發率飆到 60%~85% 且期末偏差被帶到 +6%~+12%）；夠寬的 cap 則無作用。
7. **購買類型不參與**：`isBuyType == true` 的轉直接跳過本節所有挑選邏輯，只做單一公平抽樣與記帳（詳見第 8 節）。

## 7. 暖機與啟用邏輯

- `overrideMode == AUTO`（預設）：`controlOn = (W >= W_MIN)`。
- `overrideMode == FORCE_ON`：忽略 `W_MIN`，強制啟用（上線前測試、或特定機台需要）。
- `overrideMode == FORCE_OFF`：強制關閉控制（該機台只做記帳、不干預結果）。
- 即使 `controlOn`，仍需 `|metric| > band` 才會實際挑選；否則單一抽樣。
- 動態帶寬讓「資料量不同的機台」自動拿到合適的鬆緊度，`W_MIN` 只是切掉「帶寬 >30%、控制無意義」的最初階段。

### 7.1 觸發方式：確定性（機率觸發暫緩）

目前為**確定性觸發**（`|metric| > band` 即修正）。評估過「超帶後以機率 p 決定是否修正」，**暫不採用**：固定 p 與 `band`／`N` 的效果重複、僅是整體調弱修正，並惡化上修不對稱。若日後 telemetry（§11）顯示「修正 episode 連續轉數過長、可能被看出規律」，再考慮改為**隨偏離程度上升的分級機率**（非固定 p），屆時需一併評估對收斂速度的影響。實作上此開關應以參數控制、預設確定性。

## 8. 多玩法 / 購買類型處理

同一款遊戲、同一 RTP 版本下會有多種玩法（基本押注、1.5× 強化、高倍購買遊戲等）。處理原則如下，**已訂死**：

1. **全部共用同一個水池**，key 不含玩法（維持三元組）。因為對帳與看資料都是以「遊戲」為單位，不拆玩法；總代看的正是遊戲層級 RTP。
2. **數學設計保證每種玩法的原生 RTP 皆 = r**，因此把所有玩法混入同一個 D 不會產生偏差，長期期望仍為 0；也**不需監控各玩法的下注佔比**。
3. **購買類型玩法（`isBuyType == true`）一律只記帳、不參與候選挑選**：
   - 仍照常更新 `Dl`、`Bl`、`W`（計入遊戲 RTP，守住總代看的口徑）。
   - 但結果一律走單一公平抽樣，**永遠不被候選挑選 steering**。
   - 理由：購買下注額極高（如 50×、100×），若被當成修正槓桿會造成過度修正與高注玩法被 steering 的疑慮；且其原生 RTP 已由設計保證 = r，無需控制。
   - **實測驗證**：購買 win/bet 變異係數約 1.0（vs 正常/ExtraBet 6～8）、單注倍數有頂（約 4～10× vs 900～1500×）；含購買 vs 排除購買對水池期末偏差影響 <0.7pp。留在池中記帳成本極低，且有時具穩定作用。
4. **`isBuyType` 由遊戲／下注類型於 spin 請求時傳入**，不以下注金額門檻推斷（避免誤判 1.5× 強化等一般玩法）。基本押注與 1.5× 強化等一般玩法照常參與候選挑選。

## 9. 邊界情況與工程注意事項

1. **除以零**：`Bl == 0`（首轉前）時 `metric` 視為 0；`W` 帶入 `band` 前先 `max(W, 1.0)`。
2. **數值精度**：用 double。λ 接近 1（1−λ = 2.5e-6）在 double 下可正確表示；`Dl`、`Bl`、`W` 皆有上限（`W → 1/(1−λ) ≈ 400k`，`Bl → avgBet/(1−λ)`），不會無限膨脹或溢位。
3. **持久化**：水池狀態需落地（DB / KV），並在服務重啟後可還原。欄位極小，讀寫成本低。
4. **衰減是「每轉」而非「每時間」**：只有發生 spin 才乘 λ。機台閒置期間狀態凍結，恢復營運時從上次值續算——符合「以轉數為單位」的語意。
5. **RTP 版本切換**：平台切換 RTP 版本 = 換到另一個水池 Key。舊版本水池保留其狀態即可，不需搬移。

### 9.1 每個 Key 的更新一致性

一轉是一次 read-modify-write（讀水池 → 決定結果 → 寫回）。同一 Key 的並發 spin 若完全不管，累積值可能因競態而錯亂。不同 Key 之間互不影響，可水平擴展。

### 9.2 嚴格序列化 vs 最終一致（待 server 定案）

**這是一個實作抉擇，建議由 server 依平台架構決定：**

- **選項 A：嚴格序列化**——同一 Key 以鎖或原子交易序列化。最精準，但熱門遊戲在單一總代下所有 spin 擠過同一把鎖，高流量時是吞吐瓶頸。
- **選項 B：最終一致（推薦評估）**——本機制是統計控制器、天生容忍雜訊：`Dl/Bl/W` 用 atomic add 累加、決策時讀一個可能稍舊的值即可。偶發競態只是雜訊，會被 40 萬轉的窗稀釋掉。可解熱點瓶頸，並支援分片累加（把池 hash 成 M 個子池、決策時聚合，換 M 倍並行）。

> 建議提給 server 的問題：「此為容忍雜訊的統計控制器，同一 key 是否需要嚴格序列化，或最終一致即可？」傾向 B。

## 10. 待調參數與上線前檢查

- **N（候選數）**：初值建議 10。N 越大控制越強、但每次「觸發」時的計算成本越高（僅在觸發時才產生 N 個候選；帶內不產生，故平均成本低）。上線後依實測的偏差收斂速度調整（需用「有持續性偏移」的池評估，因一般高流量池觸發率可能為 0）。
- **VOL 上線檢查線**：全域參數以 `VOL = 15` 為天花板調校。**任何新上線遊戲若波動係數 > 15，該機台會偏向過度觸發**，需個別評估（單獨給參數，或接受較強控制）。上線前應確認 `該遊戲 vol ≤ 15`。決定此全域 VOL 時，應以「**含各玩法、押注加權後**」的實際波動為準，而非僅看基本玩法。
- **λ / ε / VOL 的耦合（三者一組，勿單獨改）**：`EPSILON` 大致應等於穩態下的 `K · VOL / sqrt(2/(1−λ))`。目前 {λ=0.9999975, ε=0.05, VOL=15} 內部自洽（滿記憶時帶寬剛好收到 5%）。若調整 λ（記憶窗）或 VOL，需連動重算 EPSILON 與 W_MIN，否則帶寬語意會脫鉤。
  - `W_MIN` 的意義：帶寬第一次收到約 30% 的那一點，即 `W_MIN ≈ (K·VOL / 0.30)² / 2`。

## 11. Telemetry / 事件 log（v1 即須落地）

> 儀表板與告警規則可上線後再規畫，但**原始事件 log 必須從 v1 就記錄**——這段資料事後補不回來，而它正是調 N、驗證帶寬、稽核修正行為的唯一依據。

**每轉至少記錄：** 水池 Key、時間、`bet`、`win`、`r`、`isBuyType`、當轉 `metric`、`band`、是否觸發 `triggered`、（觸發時）`N` 與選中候選的 `win`。

**建議後續可由 log 導出的觀測項：**
- 每池 `metric` 時序、觸發率。
- **修正 episode 長度**（連續觸發轉數）——用來判斷是否需要 §7.1 的分級機率。
- 「連續 X 轉卡在帶外」告警——通常代表某遊戲 VOL 設錯或數學模型有 bug。

| 單注 cap | 無 | 已評估不採用（§6.6） |
| 購買 steering | 關 | 只記帳不挑選（§8） |
| 並行一致性 | 待 server 定案 | 傾向最終一致（§9.2） |

## 13. 階段實作計畫

**總原則：先把「記帳」做對、再開「修正」、最後才「全量＋運營」。** 因為 candidate steering 會直接改變實際 RTP 與營收，風險最高，必須排在「帳算得準、telemetry 看得到、且能一鍵回退」之後，並先小範圍試點再放量。每一階段都可獨立上線、獨立回退。

> 全域回退開關（kill switch）在第 1 階段就要具備：一鍵把所有池切成 `FORCE_OFF`（等同純 RNG），是後續每一階段的安全網。

### 第 1 階段：記帳與觀測（Shadow Mode，完全不 steer）

**目標：** 把水池的資料模型、每轉累積、持久化、事件 log 全部做完並上線，但**結果一律走單一公平抽樣，不做任何候選挑選**。等於在真實流量上「只記帳、只觀測」。

**交付項：**
- 水池狀態模型（`Dl`/`Bl`/`W`/`overrideMode`）與持久化（DB/KV），重啟可還原。
- 每轉流程 §4 的第 1、2、4、5、6 步（含 `metric`／`band` 計算），但第 3 步**強制單抽**（全域等同 shadow）。
- 事件 log（§11）完整落地：每轉一筆、欄位齊全、可查詢。
- 全域 kill switch（一鍵 `FORCE_OFF`）。
- 離線回放工具：能用一批 spin 重算 `Dl/Bl/W/metric/band` 作為對照基準。

**驗收標準：**
- **記帳正確性**：離線回放對同一批 spin 重算的 `Dl/Bl/W/metric/band`，與線上逐筆一致（相對誤差 < 1e-9）。
- **零影響證明**：本階段所有結果與「關閉本系統」的對照組**逐筆相同**——證明 shadow 完全不動玩法/RTP。
- **對帳一致**：水池累積的 bet/win 總量與真實交易帳吻合。
- **並行正確**：壓測下同一 Key 的累積值不因競態錯亂（與序列化基準比對，§9.2 的方案在此驗證）。
- **效能**：每轉額外延遲與 DB 讀寫在預算內（無明顯 regression）。
- **可觀測**：能從 log 畫出任一池的 `metric`／`band` 時序與（假想的）觸發率。

> 產出價值：在**零風險**下拿到真實流量的 metric/band 軌跡，作為第 2 階段設定 pilot、驗證帶寬是否合理的依據。

### 第 2 階段：候選挑選上線（Steering，小範圍試點）

**目標：** 實作候選挑選，並只在**少數試點池**（canary 總代或指定機台，用 `FORCE_ON`）開啟，其餘維持 shadow。驗證修正確實能把持續性偏移拉回、且不傷害玩法與 RTP。

**交付項：**
- `engine.generateCandidates(N)` ＋ `argmin |c.win − target|` 選擇（§6）。
- 觸發判斷 `controlOn && |metric|>band`（確定性，§7.1）、暖機/`W_MIN`/動態帶寬 gating。
- 購買類型排除 steering（`isBuyType` 只記帳不挑選，§8）。
- 每池 `overrideMode` 切換能力（至少後端可設 `AUTO/FORCE_ON/FORCE_OFF`）。

**驗收標準：**
- **觸發正確**：以 log 驗證「`|metric|>band` 才挑選、帶內單抽」100% 符合。
- **候選合法**：對 `generateCandidates` 產出的大量候選做分布檢定（卡方／KS），與原生 RNG 分布無顯著差異——證明只「選擇」不「捏造」。
- **購買不 steer**：所有 `isBuyType` 轉皆單抽，log 中 0 例外。
- **收斂**：對試點池人為造一個持續偏移，`metric` 能在合理轉數內回到帶內；記錄 episode 長度。
- **收手正確**：`metric` 回帶內的下一轉即恢復單抽（無殘留 hysteresis）。
- **RTP 守住**：試點池在測試期實際 RTP 貼近目標（容差內），且相對 shadow 對照池，持續性偏移明顯較小（A/B 對照）。
- **效能**：候選僅在觸發時生成；平均延遲增量可接受、觸發時 p99 延遲在預算內。
- **回退有效**：`FORCE_OFF` 立即恢復純 RNG。

### 第 3 階段：全量推廣與運營化

**目標：** 把 steering 以 `AUTO` 為預設放到全部池，並補齊運營所需的管理、告警、對帳串接。

**交付項：**
- 全池 `AUTO` 預設；`overrideMode` 管理 API/介面（可對任一 Key 設 `AUTO/FORCE_ON/FORCE_OFF`，即時生效）。
- 儀表板：每池 `metric` 時序、觸發率、貢獻度排序（下注佔比 × 偏差幅度）。
- 告警：「連續 X 轉卡在帶外」、「episode 過長」、「觸發率異常」。
- VOL 上線檢查 gate：新遊戲上線前若 `vol > 15` 會被標記/擋下（§10）。
- 月對帳串接：驗證總代加總 RTP 對目標。

**驗收標準：**
- **全量穩定**：全池 `AUTO` 運行，無異常累積、無效能瓶頸（§9.2 方案在全量壓力下成立）。
- **Override 生效**：對任一 Key 切換 `AUTO/FORCE_ON/FORCE_OFF` 即時生效，log 可追。
- **告警可靠**：合成一個「卡在帶外」與一個「episode 過長」的池，告警如期觸發。
- **對帳達標**：至少一個完整對帳週期，總代加總 RTP 落在目標帶內；用貢獻度排序能正確定位偏移最大的機台。
- **VOL gate**：以一個 `vol > 15` 的測試遊戲驗證會被標記。
- **全域 kill switch**：一鍵全 `FORCE_OFF` 驗證可即時恢復純 RNG。

### 第 4 階段（未來優化，非必要，依 telemetry 決定）

**目標：** 只有當前三階段的實測資料顯示需要時才做，避免過早優化。

**候選項與觸發條件：**
- **分級機率觸發**（§7.1）：若 telemetry 顯示修正 episode 連續轉數過長、可能被看出規律，改為「機率隨偏離程度上升」。
- **分片累加 / 最終一致優化**（§9.2）：若熱門 Key 出現鎖瓶頸，導入 hash 分片子池 + 聚合。
- **每遊戲 VOL / λ**：若單一全域 `VOL=15` 造成部分高波動遊戲過度觸發、或記憶窗對某些遊戲明顯不合適，改為 per-game 參數。

**驗收標準：** 每項各自以「導入前後的觸發率／收斂速度／延遲／穩態偏差」對照，證明有改善且無回歸。
